Formule générale (N sous-questions)

Vanilla : 1 appel (Mistral Large)
Décomp / Décomp+RAPTOR : N+2 appels   [1 Mistral Large decompose + N Claude Haiku SQ + 1 Mistral Large synth]
Self-Ask : 1 + n_hops appels (Mistral Large, séquentiel)

Overhead relatif vs Vanilla (N=5, décomp) : 7 appels = +600%
Overhead relatif vs Vanilla (Self-Ask, 1.6 hops moy.) : 2.6 appels = +160%

Parallélisabilité des étapes

Les N réponses aux sous-questions (Claude Haiku) sont indépendantes et peuvent être lançées en parallèle (async/gather). La décomposition (Mistral Large) et la synthèse (Mistral Large) sont séquentielles (dépendance causale). En production avec parallélisation des N SQ, la latence effective est :
t_eff ≈ t_decomp + max(t_SQ) + t_synth (au lieu de t_decomp + N × t_SQ + t_synth).
Pour Self-Ask, chaque hop dépend du précédent — aucune parallélisation possible.

D · Réponses aux reviewers

Basées uniquement sur les métriques exactes (appels LLM + latence) et le modèle analytique N+2. Les tokens ne sont pas mentionnés (non fiables).

Reviewer 2, point 4 : overhead LLM et latence

Draft (en) :

Our multi-step RAG pipeline (Décomp+RAPTOR) requires N+2 LLM calls per query by design: one decomposition call (Mistral Large, max_tokens=600), N=5 parallel sub-question answering calls (Claude Haiku), and one synthesis call (Mistral Large, max_tokens=2500). For comparison, the vanilla baseline issues a single LLM call per query, and the Self-Ask variant issues 1+n_hops calls (empirical mean: 2.6 calls, measured over 109 queries). The N sub-answer calls are fully independent and can run in parallel (async gather), so the effective wall-clock latency is bounded by t_decompose + max(t_sub_answer) + t_synthesize, not their sum. Measured across all 109 evaluation queries, end-to-end latency for Décomp+RAPTOR is 60.8 s (σ=18.3 s, median=63.4 s), compared to 13.1 s for the vanilla baseline (overhead ×4.7). The RAPTOR index (674 hierarchical summaries, constructed offline once with Mistral Small) adds no per-query latency: retrieval is a pure vector similarity search over the pre-built index. Token consumption per query was not instrumented in the evaluation harness (see §E); a future instrumented run would be needed to report reliable input/output token counts.

Reviewer 3 : complexité de la pipeline multi-étapes

Draft (en) :

We acknowledge the increased architectural complexity of our pipeline relative to a single-call RAG system. The pipeline consists of three online stages: (1) question decomposition into N sub-questions (Mistral Large), (2) N parallel sub-question answering calls over RAPTOR-indexed sources (Claude Haiku), and (3) final answer synthesis (Mistral Large). An optional fourth stage — per-dimension LLM scoring — is used during evaluation only and incurs no production overhead. This design is a deliberate response to the structure of our task: territorial well-being questions span heterogeneous source types (verbatim survey responses, quantitative indicators, administrative records) and typically require aggregating evidence across multiple sub-dimensions (e.g., mobility satisfaction by commune). Decomposition enables targeted retrieval per sub-dimension; RAPTOR hierarchical pre-summarisation reduces the retrieval burden at query time. The N=5 sub-answer calls are parallelisable, and measured latency of 61 s end-to-end (median 63 s) is compatible with offline batch use, the primary deployment mode for this research tool. This architecture is consistent with established multi-step RAG designs (sub-question decomposition in LlamaIndex, FLARE, Self-RAG), and the added complexity is justified by the empirical performance gains we report.

E · Limites d'instrumentation — mémoire

Limite principale : le harness ne persiste pas le contenu intégral des contextes.

Lors des runs d'ablation, le JSON de sortie archivait le nombre de sources (n_sources) mais pas leur contenu textuel pour toutes les configurations. Concrètement :
  • v_decomp_old & v_decomp_raptor : sub_questions non archivées (0/109 entrées).
  • v_decomp_no_typing_v2_legacy : sources archivées mais content="" (jusqu'à 70 sources sans texte). Sous-questions archivées avec texte.
  • v_vanilla_k10/k25 & v_selfask : sources et réponses archivées correctement.

Conséquence : les tokens input ne sont pas estimables de manière fiable pour les configs décompositionnelles. Une instrumentation future devrait logguer directement les usage.input_tokens et usage.output_tokens retournés par chaque appel API (disponibles dans les réponses Mistral et Anthropic) et les persister dans le JSON de run.
